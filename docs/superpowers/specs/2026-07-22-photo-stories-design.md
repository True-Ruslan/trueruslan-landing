# Photo Stories — дизайн раздела «Фото»

## Контекст

Текущий раздел «Фотографии» представляет собой короткую Markdown-страницу с несколькими отдельными изображениями. Он функционален, но визуально и концептуально заметно слабее остальных частей сайта и не поддерживает дальнейшее органичное развитие.

Новая версия раздела должна стать личным визуальным архивом внутри инженерного сайта: спокойным, атмосферным, хронологичным и достаточно выразительным, но без превращения в социальную сеть или отдельный медиасервис.

## Цель

Создать статический фотораздел, в котором:

- основная единица контента — история-альбом;
- истории идут в обратной хронологии;
- каждый альбом имеет собственную отдельную страницу;
- страница альбома строится как небольшая визуальная история с cinematic hero и editorial-композицией;
- отдельные фотографии открываются в fullscreen lightbox;
- существующие одиночные фотографии сохраняются в компактном блоке «Из архива»;
- без JavaScript весь основной контент остаётся доступен;
- архитектура остаётся static-first и build-time driven.

## Принятые продуктовые решения

### Формат раздела

Выбран гибридный формат: визуально сильная фотогалерея + короткие личные истории.

Подписи живые, но сдержанные:

- место и/или дата;
- одна-две короткие фразы от первого лица;
- без пафоса, длинных дневниковых заметок и «социальной» подачи.

### Основная сущность

Одна история = один альбом.

Пример:

- «Карелия · 2026»;
- Сортавала · Рускеала · Ладожские шхеры;
- краткая аннотация;
- количество фотографий;
- отдельная страница истории.

### Порядок показа

Главный порядок — обратная хронология.

Категории используются только как фильтры и дополнительный контекст:

- Путешествия;
- Учёба и события;
- Люди;
- Обычные моменты.

Категории не определяют основную структуру страницы.

### Текущие фотографии

Существующие одиночные фотографии не превращаются искусственно в альбомы.

Они остаются отдельным блоком «Из архива» внизу основной страницы и используют тот же fullscreen lightbox.

## Информационная архитектура

### Основная страница

Маршрут:

`/photos`

Структура:

1. Атмосферный intro-блок.
2. Небольшие фильтры категорий.
3. Хронологические группы по годам.
4. Карточки историй-альбомов.
5. Блок «Из архива» с существующими одиночными кадрами.

### Страница альбома

Маршрут:

`/photos/<slug>`

Пример:

`/photos/karelia-2026`

Структура:

1. Cinematic hero почти на весь viewport.
2. Название истории.
3. Место, дата, категория и количество фотографий.
4. Короткая личная вступительная заметка.
5. Editorial-фотосерия.
6. Навигация к соседним историям при наличии.
7. Возврат к общему фотоархиву.

## Визуальное направление

### Общая эстетика

Раздел визуально спокойнее технических страниц сайта.

Характер:

- тёмная или приглушённая фон-подложка там, где это уместно;
- крупные фотографии;
- минимум декоративного шума;
- большая роль воздуха и ритма;
- мягкие переходы и hover-состояния;
- общий язык типографики и навигации сохраняется совместимым с остальным сайтом.

Раздел не должен выглядеть как отдельный чужой продукт.

### Карточки альбомов

Карточка содержит:

- крупную обложку;
- название;
- место/контекст;
- дату;
- количество фотографий;
- категорию как вторичный маркер.

Карточки могут отличаться по размеру в зависимости от композиции года, но DOM-порядок всегда остаётся хронологическим и логичным.

### Cinematic hero

Hero страницы альбома:

- занимает значительную часть первого экрана;
- использует выбранную cover-фотографию;
- сохраняет читаемость текста на светлых и тёмных изображениях;
- не должен обрезать ключевой объект изображения без необходимости;
- на мобильных устройствах адаптируется по высоте без потери содержания.

Поверх или непосредственно под hero показываются:

- название;
- место;
- дата;
- короткий вводный текст;
- количество фотографий.

## Editorial-фотосерия

Фотографии не выводятся однообразной сеткой 3×3.

Допустимые композиционные паттерны:

- один широкий кадр;
- один вертикальный кадр с большим количеством воздуха;
- два связанных вертикальных кадра рядом;
- два или три связанных кадра в компактной серии;
- редкие текстовые подписи между блоками.

Композиция определяется данными альбома через ограниченный набор layout-вариантов, а не произвольным HTML в данных.

Рекомендуемые layout-типы:

- `wide`;
- `portrait`;
- `pair`;
- `triptych`;
- `standard`.

На узких экранах все варианты деградируют в последовательный одноколоночный поток без потери порядка фотографий.

## Fullscreen lightbox

Lightbox используется и для альбомов, и для «Из архива».

### Обязательное поведение

- открытие по клику на фотографию;
- fullscreen overlay;
- сохранение исходного aspect ratio;
- отсутствие принудительного crop;
- стрелки `←` и `→`;
- клавиатурная навигация;
- `Esc` для закрытия;
- свайпы на touch-устройствах;
- кнопка закрытия;
- счётчик вида `05 / 14`;
- подпись, место и/или дата при наличии;
- предзагрузка соседнего кадра;
- возврат focus в исходную фотографию после закрытия;
- блокировка прокрутки страницы во время открытия.

### Deep link

Состояние конкретной фотографии отражается через hash:

`/photos/karelia-2026#photo-5`

Прямая ссылка должна:

- открывать страницу альбома;
- при доступном JavaScript сразу открывать соответствующий кадр;
- без JavaScript приводить пользователя к доступной фотографии на странице через обычный anchor/fallback.

Закрытие lightbox очищает или корректно восстанавливает hash без перезагрузки страницы.

## Данные

### Canonical registry

Основной источник данных:

`data/photo-albums.json`

Он является единственным canonical registry для альбомов.

Минимальная модель альбома:

```json
{
  "slug": "karelia-2026",
  "title": "Карелия",
  "date": "2026-07",
  "year": 2026,
  "places": ["Сортавала", "Рускеала"],
  "category": "travel",
  "summary": "Короткая личная аннотация.",
  "cover": "01.jpg",
  "published": true,
  "photos": []
}
```

Минимальная модель фотографии:

```json
{
  "id": "photo-1",
  "src": "01.jpg",
  "alt": "Осмысленное описание изображения",
  "caption": "Короткая подпись при необходимости.",
  "place": "Сортавала",
  "date": "2026-07-24",
  "layout": "wide"
}
```

Поля, не нужные для конкретного кадра, могут отсутствовать.

### Архив

Существующие одиночные фотографии хранятся отдельно от альбомов, чтобы не загрязнять модель истории.

Предпочтительный источник:

`data/photo-archive.json`

Он содержит:

- src;
- alt;
- title;
- краткую подпись;
- дату или год при наличии;
- порядок.

## Файловая структура изображений

Предпочтительно:

```text
assets/images/photos/
  albums/
    karelia-2026/
      cover.jpg
      01.jpg
      02.jpg
      ...
  archive/
    semihatov.jpg
    magister.jpg
    avatar.png
```

На первом этапе существующие пути могут быть сохранены ради безопасной миграции, если перенос создаёт лишний риск. Canonical registry не должен зависеть от того, выполнен ли физический перенос сразу.

## Build-time pipeline

Новая функциональность остаётся static-first.

Build-time код должен:

1. Валидировать `photo-albums.json` и `photo-archive.json`.
2. Проверять уникальность `slug` и `photo.id` в пределах альбома.
3. Проверять существование всех файлов изображений.
4. Проверять обязательный `alt`.
5. Сортировать опубликованные альбомы по дате.
6. Группировать их по годам.
7. Генерировать данные для `/photos`.
8. Генерировать отдельную страницу для каждого опубликованного альбома.
9. Генерировать lightbox manifest в статической разметке или безопасном inline JSON.
10. Не делать runtime-запросов к backend, CMS или внешнему API.

## Progressive enhancement

Без JavaScript:

- `/photos` показывает все опубликованные альбомы в правильной хронологии;
- фильтры могут отсутствовать или быть обычными anchor-навигационными элементами;
- страницы альбомов полностью содержат всю фотосерию;
- каждая фотография доступна как обычное изображение/ссылка;
- hash anchors остаются рабочими.

С JavaScript добавляются:

- мгновенная фильтрация категорий;
- fullscreen lightbox;
- клавиатурная и touch-навигация;
- deep-link синхронизация;
- предзагрузка соседних изображений.

## Производительность

Обязательные правила:

- изображения ниже первого экрана lazy-load;
- hero и первая критичная фотография не должны лениво загружаться, если это ухудшает LCP;
- width/height или aspect-ratio задаются заранее для предотвращения layout shift;
- browser не должен загружать полноразмерные изображения всех альбомов на `/photos`;
- карточки используют оптимальные preview/cover-версии, если pipeline уже позволяет их подготовить;
- lightbox не должен предзагружать весь альбом сразу — только соседние кадры.

Отдельный image-CDN или внешний image-processing backend в этот релиз не добавляется.

## Доступность

### Основные требования

- все изображения имеют содержательный `alt`;
- декоративные изображения используют пустой alt только осознанно;
- карточки альбомов доступны с клавиатуры;
- focus states видимы;
- lightbox реализует focus trap;
- `Esc` закрывает lightbox;
- aria-label у кнопок навигации понятны;
- счётчик не является единственным способом понять порядок;
- prefers-reduced-motion отключает необязательные анимации;
- контраст текста на hero соответствует доступным значениям;
- порядок DOM соответствует визуальной и хронологической логике.

## Responsive-поведение

### Desktop

- широкий cinematic hero;
- свободная editorial-композиция;
- пары и триптихи используются по назначению;
- lightbox максимально использует viewport.

### Tablet

- сложные композиции упрощаются;
- сохраняется визуальный ритм;
- touch-навигация lightbox обязательна.

### Mobile

- один основной поток;
- пары и триптихи перестраиваются последовательно;
- hero не блокирует доступ к заголовку и метаданным;
- фильтры прокручиваются горизонтально или компактно переносятся;
- кнопки lightbox имеют touch-friendly размер;
- свайпы не конфликтуют с вертикальным scroll после закрытия overlay.

## Интеграция с навигацией и поиском

- существующий пункт «Фото» сохраняется и ведёт на новую страницу;
- альбомы могут индексироваться внутренним поиском как отдельные страницы;
- Cmd/Ctrl+K может находить отдельные опубликованные истории после генерации поискового индекса;
- архивные одиночные фото отдельными поисковыми документами не становятся.

## SEO и sharing metadata

Для каждого альбома build-time генерируются:

- title;
- description;
- canonical URL;
- Open Graph title/description;
- Open Graph image на основе cover;
- базовые структурированные метаданные страницы без избыточной schema-разметки.

Основная страница `/photos` получает собственные description и OG metadata.

## Ошибки данных

Build должен завершаться ошибкой при:

- дублирующемся slug;
- дублирующемся photo id внутри альбома;
- отсутствующем cover;
- отсутствующем image-файле;
- пустом обязательном alt;
- неизвестном category;
- неизвестном layout type;
- опубликованном альбоме без фотографий.

Неполные необязательные подписи, место или точная дата не являются ошибкой.

## Тестирование

### Unit / data tests

Проверить:

- schema validation;
- сортировку по дате;
- группировку по годам;
- категории;
- уникальность slug/id;
- генерацию маршрутов;
- mapping archive data;
- fallback при отсутствующих необязательных полях.

### Build / integrity tests

Проверить:

- все сгенерированные страницы существуют;
- все image references разрешаются;
- нет битых внутренних ссылок;
- no-JS HTML содержит фотографии и текст;
- OG metadata присутствует на страницах альбомов.

### Browser smoke

Обязательные сценарии:

1. `/photos` открывается без горизонтального overflow.
2. Альбомы идут по убыванию даты.
3. Фильтр категории скрывает/показывает карточки без изменения DOM-порядка.
4. Открытие карточки ведёт на страницу альбома.
5. Hero и фотосерия видимы.
6. Клик по фото открывает lightbox.
7. `→` и `←` переключают изображения.
8. `Esc` закрывает lightbox.
9. Hash обновляется и direct-link открывает правильный кадр.
10. Focus восстанавливается после закрытия.
11. Архивные фото используют тот же lightbox.
12. Mobile viewport не имеет overflow.
13. Reduced motion не ломает интерфейс.

### Accessibility

Сохранить существующие Axe/Lighthouse quality gates и добавить фото-страницы в browser/a11y smoke там, где это не создаёт чрезмерное дублирование тестов.

## Миграция существующей страницы

Текущая страница «Фотографии» заменяется новой структурой без потери существующего публичного маршрута.

Существующие фотографии:

- Семихатов;
- защита магистерской;
- аватар;

переносятся логически в «Из архива» и получают корректные alt/подписи.

Старые ссылки на `/photos` или эквивалентный текущий публичный route не должны ломаться.

## Не входит в scope

В этой версии не добавляются:

- аккаунты;
- комментарии;
- лайки;
- пользовательская загрузка фотографий;
- CMS;
- backend;
- база данных;
- runtime GitHub API;
- бесконечная лента;
- социальные механики;
- геокарта;
- EXIF browser;
- автоматическая AI-генерация подписей;
- внешний image CDN как обязательная зависимость.

## Критерии готовности

Функция считается завершённой, когда:

1. `/photos` визуально работает как хронологический каталог историй.
2. Каждый опубликованный альбом имеет собственную страницу.
3. Cinematic hero и editorial-фотосерия адаптивны.
4. Fullscreen lightbox работает мышью, клавиатурой и touch.
5. Deep links на фотографии работают через hash.
6. Существующие фотографии доступны в «Из архива».
7. Без JavaScript основной контент полностью доступен.
8. Build-time validation блокирует некорректные данные.
9. Нет horizontal overflow на основных desktop/mobile viewport.
10. Существующие site integrity, accessibility и visual quality gates проходят.
11. Новые browser smoke-тесты проходят.
12. В `master` не добавляются демонстрационные фейковые альбомы: архитектура готова к реальным историям, а текущие одиночные фото остаются архивом до появления полноценного набора кадров.

## Архитектурный принцип

Функция следует существующей стратегии проекта:

**static-first + build-time intelligence + progressive enhancement**.

Контент остаётся обычным индексируемым HTML, данные — локальными version-controlled registry, а JavaScript добавляет только удобство и интерактивность, не являясь условием доступа к содержанию.
