# Проектирование server-authoritative AI NPC pipeline

Когда я только начал собирать LivingWorld, самой очевидной частью казалось подключение LLM: передать текст, получить ответ, показать его игроку.

Но довольно быстро стало понятно, что для многопользовательской игры это почти не решает главную задачу. Если AI-персонаж действительно должен быть частью мира, нужно отдельно понять, кто владеет разговором, как хранится память, что делать с голосом, как отменять старые запросы и где проходит граница между предложением модели и реальным действием в игре.

В итоге я пришёл к server-authoritative схеме: session ownership, контекст, память, provider orchestration и разрешение действий остаются под контролем сервера.

## 1. Я начинаю не с LLM, а с сессии

До любого AI-request сервер уже должен знать:

- какой игрок владеет разговором;
- с каким NPC он говорит;
- активна ли сессия;
- допустим ли текущий канал ввода;
- нужно ли отменить предыдущую работу.

Для меня это стало базовой моделью проекта. Если сначала не решить владение сессией, потом очень трудно аккуратно добавить voice, cancellation или несколько параллельных игроков.

Один NPC не должен случайно оказаться участником двух независимых разговоров только потому, что одновременно пришли два запроса к модели.

## 2. Text и voice я свожу в один разговорный pipeline

Игрок может писать или говорить голосом, но после распознавания я не хочу поддерживать две разные версии бизнес-логики.

```text
Text input ───────────────────────┐
                                  ▼
Voice → PCM → STT → normalized message
                                  │
                                  ▼
                          conversation core
```

Voice для меня здесь — ещё один способ получить нормализованное сообщение. После этого разговор должен идти по тем же правилам, что и текстовый ввод.

Так транспорт не начинает диктовать устройство самого диалога.

## 3. LLM не должна быть authority

Это, пожалуй, самая важная граница во всей схеме.

Модель может предложить текст или намерение, но я не хочу, чтобы её output напрямую менял Minecraft-мир.

```text
LLM output
   │
   ▼
structured intent
   │
   ▼
authorization / validation
   │
   ├── rejected
   └── allowed → game action
```

Перед действием всё равно нужно проверить его тип, параметры, состояние NPC, контекст сессии и правила мира.

Особенно важным это становится из-за пользовательского текста внутри prompt. Для меня prompt injection не должен иметь путь, по которому он неожиданно превращается в game-server command injection.

## 4. Память я держу отдельно от prompt

Сначала довольно естественно представить память как «просто отправлять модели предыдущий transcript».

Но такая схема быстро начинает плохо масштабироваться и слишком сильно связывает данные персонажа с конкретным форматом prompt.

Поэтому полезнее отдельно хранить:

- короткий context текущего разговора;
- устойчивые факты и отношения NPC;
- world context, который можно собрать заново;
- provider-specific представление prompt.

Тогда можно менять LLM или способ сборки контекста, не переписывая саму модель памяти.

## 5. Cancellation пришлось воспринимать как обычный control flow

Pipeline содержит несколько потенциально медленных стадий:

```text
STT → LLM → TTS
```

За это время игрок может завершить разговор, отключиться, начать новый запрос или NPC может вообще перестать существовать в актуальном контексте.

Поэтому cancellation для меня перестала быть «дополнительной обработкой ошибки». Она проходит через весь pipeline как нормальный сценарий жизни системы.

Старый ответ, который уже никому не нужен, не должен внезапно прийти позже и изменить состояние новой сессии.

## 6. Fallback оказался важнее красивого happy path

Внешний AI/voice pipeline почти гарантированно когда-нибудь ломается частично:

- voice не распознался;
- LLM недоступна;
- TTS упал после успешного текстового ответа;
- provider завис;
- persistence не смогла сохранить новое состояние.

Мне важно, чтобы эти ошибки не слипались в один общий «AI не работает».

Например:

- STT failure не должен ломать текстовый канал;
- TTS failure не должен уничтожать уже готовый subtitle/text response;
- provider timeout должен освобождать ресурсы сессии;
- persistence failure не должен незаметно создавать ложное ощущение сохранённой памяти.

Чем лучше разделены эти возможности, тем проще системе деградировать понятно, а не падать целиком из-за одного внешнего компонента.

## 7. Что я действительно считаю проверенным

В текущем LivingWorld automated CI покрывает unit/package/reproducibility checks, multi-actor resilience scenarios, Fabric game tests, persistence/restart behavior, action/injection rejection, cancellation, fallback paths и synthetic multi-session ownership.

При этом я сознательно не ставлю знак равенства между этим и реальной multiplayer-приёмкой.

Двухклиентный voice acceptance, качество русского STT, человеческая оценка positional TTS и staging provider degradation остаются отдельной release-candidate границей.

Мне кажется важным прямо разделять то, что доказано автоматикой, и то, что ещё требует живой проверки.

## Что я в итоге для себя сформулировал

Чем дольше я работаю с такими системами, тем меньше мне нравится идея «AI как центр приложения».

Мне ближе другая модель:

> AI — это одна из возможностей системы, а не источник истины всей системы.

Server-authoritative session model, provider abstraction, отдельная память и action authorization позволяют использовать сильные стороны LLM, не отдавая модели контроль над жизненным циклом игрового мира.

Пока это один из главных принципов, вокруг которых я продолжаю строить LivingWorld.
