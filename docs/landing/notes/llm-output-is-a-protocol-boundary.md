# Почему успешный ответ LLM ещё не означает успешный контракт

Когда я подключаю LLM к приложению, очень легко мысленно упростить happy path до такой схемы:

```text
request → provider → 200 OK → JSON → готовое решение
```

Но между `200 OK` и «готовым решением» на самом деле находится одна из самых важных границ системы.

Provider может успешно принять запрос, модель может успешно сгенерировать ответ, HTTP-запрос может завершиться без ошибки — и при этом результат всё ещё может быть **невалидным входом для моего приложения**.

На LivingWorld я в итоге стал относиться к structured output модели не как к удобному способу получить объект, а как к отдельному внешнему protocol boundary.

## 1. Самая опасная ошибка — считать transport success contract success

У внешнего AI-вызова есть несколько разных уровней успеха.

Например:

```text
transport success
        ↓
provider success
        ↓
syntactically valid response
        ↓
valid application contract
        ↓
authorized domain effect
```

Это не одно и то же.

HTTP-запрос может завершиться успешно, но тело ответа оказаться не JSON.

JSON может быть синтаксически корректным, но иметь неизвестные поля.

Поля могут называться правильно, но содержать значения другого типа.

Даже полностью валидный по схеме объект ещё не обязательно имеет право менять persistent state или игровой мир.

В текущем LivingWorld эта граница видна прямо в основном turn flow:

```text
LLM proposal
→ strict JSON validation
→ deterministic persistence policy
→ live action authorization
→ durable/live effects
```

Для меня здесь важно именно слово `proposal`.

Ответ модели — это предложение внешней системы. До прохождения следующих границ он не становится частью authoritative state.

## 2. «Почти правильный JSON» всё равно остаётся неверным входом

Самые неприятные ответы не всегда выглядят полностью сломанными.

Гораздо коварнее ответ, который визуально кажется почти правильным.

Например, приложение ожидает:

```json
{
  "speech": "Идём.",
  "emotion": "NEUTRAL",
  "relationshipDelta": {
    "trust": 1,
    "respect": 0,
    "fear": 0,
    "affinity": 0
  },
  "memoryCandidates": [],
  "actions": [{"type": "FOLLOW"}]
}
```

Но внешняя система может вернуть форму, отличающуюся всего одной деталью:

```text
валидный JSON + ещё один trailing token
```

или:

```json
{"trust": "1"}
```

вместо числа.

Или:

```json
{"trust": 1.0}
```

Или `null` там, где доменная модель требует конкретное значение.

Отдельная категория — массивы: `null` вместо action, повторяющиеся действия или логически конфликтующие команды вроде одновременных `FOLLOW` и `STOP_FOLLOWING`.

Технически часть этих payload можно «спасти» достаточно агрессивным parser-ом.

Но тогда система начинает сама додумывать смысл ответа модели.

И это уже другой контракт.

## 3. Почему я отключаю удобные coercion

Многие serializers умеют быть дружелюбными.

Строка `"1"` может автоматически стать числом `1`.

`1.0` можно привести к integer.

Отсутствующее или `null`-значение иногда можно заменить default `0`.

Для обычного пользовательского ввода такая терпимость иногда полезна. На trust boundary structured LLM output она может скрыть реальное нарушение протокола.

В LivingWorld parser намеренно настроен строже:

- unknown fields вызывают rejection;
- trailing tokens после корректного объекта запрещены;
- `null` для primitive domain values запрещён;
- float-to-integer coercion отключён;
- scalar coercion отключён.

Это означает, что следующие значения остаются **разными состояниями протокола**:

```text
1
"1"
1.0
null
```

Я не хочу, чтобы serializer тихо решал за доменную модель, что автор внешнего ответа «наверное имел в виду».

Если контракт требует integer — внешний ответ должен содержать integer.

## 4. Parser здесь — trust boundary, а не convenience helper

Раньше parser я бы легко воспринимал просто как технический переход:

```text
JSON string → Java object
```

Сейчас я вижу его иначе:

```text
untrusted external output
        ↓
strict syntax/schema parsing
        ↓
required-field validation
        ↓
domain bounds
        ↓
whitelists + consistency checks
        ↓
accepted proposal
```

В текущем `AiDecisionParser` отдельно проверяются не только JSON и типы.

Есть доменные ограничения:

- максимальная длина `speech`;
- ограниченный диапазон `relationshipDelta`;
- bounded количество и размер memory candidates;
- максимум два action;
- точный whitelist action types;
- запрет duplicates;
- запрет конфликтующих действий.

Это важно, потому что JSON Schema в широком смысле ещё не описывает всю бизнес-семантику.

Объект может быть технически десериализуемым и при этом бессмысленным или недопустимым для конкретной системы.

Ещё одна полезная граница — ошибки наружу нормализуются в категории вроде `malformed JSON`, `unknown field`, `invalid field type`, а не превращаются в сырое содержимое provider response.

Так диагностическая модель не требует отдавать потенциально чувствительный или непредсказуемый внешний payload пользователю.

## 5. Валидный JSON всё ещё не authority

Даже после успешного parsing я не считаю `AiDecision` приказом системе.

Это следующий важный уровень.

Например, модель может корректно предложить:

```json
{"type": "FOLLOW"}
```

Action известен, тип корректен, JSON идеален.

Но сервер всё равно должен проверить актуальное состояние:

- существует ли ещё нужная conversation session;
- владеет ли ей этот игрок;
- жив ли NPC;
- находится ли он в допустимом мире и радиусе;
- разрешено ли действие сейчас.

То же самое относится к persistent state.

`relationshipDelta` и `memoryCandidates` в LivingWorld являются предложениями модели, а не автоматическим правом менять durable truth.

Поэтому цепочка специально разделена:

```text
parse/validate
≠
persist
≠
authorize live action
```

Если объединить эти этапы, ошибка одного внешнего JSON начинает получать слишком большой радиус поражения.

## 6. Fallback — часть protocol design

Malformed response — не исключительная ситуация, которую можно отложить до «обработаем потом».

Если внешний provider является частью runtime pipeline, неправильный ответ входит в нормальную модель отказов системы рядом с timeout, rate limit и недоступным endpoint.

В LivingWorld acceptance boundary отдельно требует проверять malformed provider response.

Ожидаемое поведение при таком отказе не выглядит как:

```text
parser exception → случайное состояние → оборванная сессия
```

Цель другая:

```text
invalid external response
        ↓
controlled rejection
        ↓
bounded sanitized fallback
        ↓
no unsafe state/world mutation
        ↓
later healthy turn can recover
```

Для меня особенно важна последняя строка.

Хорошая degradation semantics должна не только безопасно завершить плохой turn, но и не отравить следующий здоровый запрос.

## 7. Tests здесь описывают сам protocol

Один из полезных эффектов strict boundary — тесты становятся почти исполняемой спецификацией внешнего контракта.

В `AiDecisionParserTest` отдельно зафиксированы случаи, которые должны быть rejected:

- unknown action;
- unknown field;
- trailing token после корректного decision object;
- string вместо integer;
- floating-point вместо integer;
- `null` вместо required numeric value;
- `null` внутри memories/actions;
- слишком много actions;
- duplicate actions;
- конфликтующие actions.

Это намного сильнее теста вида «валидный JSON нормально парсится».

Happy path доказывает только один пример.

Negative contract tests фиксируют границы того, **что система обещает не интерпретировать**.

## Что я в итоге для себя сформулировал

Главный вывод сейчас для меня звучит так:

> **Provider success не равен contract success.**

LLM может быть вероятностной системой, но граница приложения вокруг неё не обязана быть вероятностной.

Structured output я стараюсь обрабатывать так же, как ответ любого внешнего API, которому нельзя полностью доверять:

1. принять bounded response;
2. строго распарсить;
3. проверить schema и типы;
4. проверить доменные ограничения;
5. превратить результат только в proposal;
6. отдельно применить persistence policy и authorization;
7. иметь контролируемый fallback на случай нарушения любого предыдущего шага.

Мне нравится эта модель ещё и потому, что она снимает лишнюю магию с LLM integration.

Снаружи находится сильный, но ненадёжный producer данных.

Внутри — обычная инженерная система с явным контрактом, trust boundaries и детерминированными правилами того, что она готова принять.
