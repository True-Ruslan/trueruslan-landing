# Quality gates для статического инженерного сайта

Когда я начинал этот сайт, относился к нему как к довольно простому статическому проекту: Markdown собрался в HTML, страница открылась — значит всё в порядке.

Потом по очереди появились несколько неприятных регрессий. Где-то сломался PDF, где-то generated search продолжал существовать, но перестал быть нормально доступен пользователю, где-то post-processing создавал битый путь, а где-то визуальное изменение проходило незаметно до публикации.

После этого я постепенно перестал считать успешный `build` достаточным доказательством того, что сайт действительно работает.

## 1. Сначала обычные tests

Самый быстрый слой по-прежнему проверяет чистую логику:

- sitemap discovery;
- SEO/post-processing;
- standalone rendering;
- local-search normalization;
- manifest validation;
- deployment-safe URL generation.

Эти тесты хорошо ловят ошибки преобразований, но почти ничего не говорят о том, что получилось в финальном `docs-html`.

## 2. Потом я проверяю уже сгенерированный сайт

После production build отдельный checker проходит по готовому artifact.

Он проверяет локальные ссылки и ресурсы с учётом HTML `<base href>` semantics. Для меня это стало важным после того, как выяснилось, что исходный Markdown может быть совершенно корректным, а ошибка появляется позже — уже на этапе генерации или post-processing.

Именно такой gate, например, помог обнаружить проблему с ресурсами Diplodoc local search.

## 3. Следующий шаг — настоящий браузер

После этого я запускаю Chromium через Playwright.

Проверяю:

- homepage, Projects и Resume;
- desktop/mobile viewport;
- HTTP failures;
- browser page errors;
- horizontal overflow;
- инициализацию visual layer;
- доступность Resume PDF как реального `application/pdf`.

Этот слой появился не из теории. Именно браузерная проверка поймала ситуацию, когда PDF был формально правильно встроен в HTML, но фактическая hydration происходила позже, чем ожидал мой код.

## 4. Accessibility и Lighthouse

Axe проверяет serious/critical accessibility violations, а Lighthouse — budgets по Performance, Accessibility, Best Practices и SEO.

Я не воспринимаю Lighthouse как абсолютную оценку сайта. Для меня это скорее ещё один независимый сигнал: если случайное изменение резко ухудшило performance или accessibility, я хочу узнать об этом до merge, а не после публикации.

## 5. Firefox и WebKit — короткая проверка, а не второй полный CI

Дублировать весь тяжёлый suite в трёх браузерах мне кажется избыточным.

Поэтому Chromium остаётся основным browser gate, а Firefox/WebKit проходят более короткий smoke по критическим страницам. Этого хватает, чтобы заметить очевидную browser-specific проблему, не увеличивая CI втрое.

## 6. Поиск я проверяю отдельно

Generated local-search page уже несколько раз оказывалась отдельным источником регрессий, поэтому у неё появился собственный smoke в настоящем Chromium.

Сейчас он проверяет не только факт существования HTML, но и реальный mount search UI, custom CSS/JS, keyboard shortcut, desktop/mobile layout, Axe и отсутствие overflow.

Этот тест как раз появился после случая, когда старый smoke был зелёным, хотя по факту он доказывал намного меньше, чем я думал.

## 7. Visual regression

Для ключевых страниц я храню versioned visual baselines desktop/mobile.

Сейчас это homepage, Projects, Resume, Engineering Map и Search.

Я специально обновляю baseline только после того, как функциональные browser checks уже зелёные. Иначе очень легко попасть в привычку «обновить screenshot, чтобы CI перестал мешать» и случайно принять настоящий дефект как новый дизайн.

## 8. Последняя граница — уже опубликованный сайт

Даже идеальный artifact ещё не доказывает, что deployment прошёл правильно.

После GitHub Pages deployment отдельный smoke проверяет реальные public URL, ключевые страницы, PDF, OpenGraph images и основные assets. Есть bounded retry, чтобы короткая задержка публикации не выглядела как постоянная ошибка.

## Как я теперь смотрю на весь pipeline

Каждая проверка отвечает на свой вопрос:

```text
Tests            → логика преобразований корректна?
Build            → сайт вообще собирается?
Integrity        → финальный artifact самосогласован?
Browser          → он реально работает в браузере?
Axe/Lighthouse   → качество укладывается в budgets?
Cross-browser    → нет очевидной несовместимости?
Visual           → внешний вид не изменился случайно?
Production smoke → опубликован именно рабочий artifact?
```

Главный вывод для меня здесь довольно простой: надёжность редко появляется из одного большого теста.

Гораздо спокойнее, когда на разных границах системы есть несколько независимых доказательств и каждый из них проверяет что-то своё.
