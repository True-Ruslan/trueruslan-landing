# MiniChess — Java domain logic

MiniChess — небольшой web-проект на Spring Boot, в котором мне было интересно поработать не столько с инфраструктурой, сколько с правилами.

Шахматы хорошо подходят для этого: снаружи приложение выглядит довольно просто, но почти любое действие быстро упирается в доменную логику — можно ли фигуре идти на эту клетку, чей сейчас ход, остаётся ли король под шахом и что вообще считается допустимым состоянием партии.

**Стек:** Java 21 · Spring Boot 3 · Spring Web · Thymeleaf · JavaScript

## Как я разделил проект

```text
Browser UI
  │
  ├── ChessPageController → HTML / Thymeleaf
  │
  └── BoardApiController → REST API
          │
          ▼
      GameService
          │
          ▼
     Chess domain/core
```

Страницу и API я разделил на разные HTTP-контроллеры, а прикладную логику игры собрал ниже, в `GameService` и доменном слое.

Мне хотелось, чтобы правила шахмат можно было проверять без браузера и чтобы UI не становился местом, где случайно живёт половина игровой логики.

## Что реализовано

- интерактивная шахматная доска;
- получение допустимых ходов для выбранной фигуры;
- серверная валидация хода;
- контроль очередности сторон;
- проверка, не оставляет ли ход собственного короля под шахом;
- определение состояния шаха;
- история ходов;
- reset новой партии;
- переворот доски в UI;
- REST API состояния доски и выполнения ходов.

## Что здесь для меня главное

### Сервер всё равно проверяет правила

Browser UI может подсветить ход или отправить команду, но я не считаю клиент источником истины.

Даже для небольшого шахматного приложения это быстро упрощает модель: интерфейс отвечает за взаимодействие с человеком, а допустимость состояния остаётся в backend-домене.

### HTTP — только один из способов добраться до логики

Контроллеры отвечают за страницу и API, но сами правила находятся ниже.

Это решение кажется довольно очевидным, но именно на подобных маленьких проектах хорошо видно, насколько проще писать тесты и менять интерфейс, когда доменная модель не знает ничего о браузере и HTTP.

### API повторяет реальные действия

Вместо одного универсального endpoint я оставил отдельные операции: получить доску, получить допустимые ходы, сделать ход, посмотреть историю, сбросить игру.

Мне такой контракт проще читать: по нему сразу видно, какие действия вообще существуют в системе.

## Проверки

В проекте заявлены отдельные тесты доски, `GameService`, REST-контроллера и page-controller. Maven-сборка поддерживает запуск тестов и генерацию JaCoCo report.

MiniChess для меня остаётся хорошим небольшим примером того, что сложность системы совсем не обязательно определяется количеством инфраструктуры. Иногда одна хорошо выраженная предметная область даёт больше материала для архитектурных решений, чем длинный список внешних сервисов.
