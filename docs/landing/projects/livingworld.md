# LivingWorld — server-authoritative AI NPCs for Minecraft

**LivingWorld** — Fabric 1.21.1 mod для MCA Reborn, над которым я работаю как над экспериментом с AI-персонажами внутри обычного Minecraft-сервера.

## С чего всё началось

Изначально идея была довольно простой: мне хотелось разговаривать с NPC не через отдельное меню с чат-ботом, а прямо в игре — текстом или голосом — и получать ощущение, что персонаж действительно находится в этом мире.

Довольно быстро стало понятно, что подключить LLM — самая простая часть задачи. Гораздо интереснее вопросы вокруг неё:

- кто именно сейчас разговаривает с NPC;
- какой контекст мира можно передать модели;
- что NPC должен помнить между репликами;
- что произойдёт, если STT, LLM или TTS временно недоступны;
- можно ли вообще позволять модели инициировать действия в игровом мире;
- как остановить уже запущенную обработку, если игрок ушёл или завершил разговор.

В итоге основной принцип проекта для меня сформулировался так: **сервер должен оставаться источником истины для сессии, контекста, памяти и любых действий**.

## Как выглядит разговор

1. Игрок приседает и кликает по живому MCA-жителю в радиусе восьми блоков.
2. Сервер создаёт эксклюзивную сессию `player ↔ NPC`.
3. Игрок использует `/livingworld say` или стандартную кнопку push-to-talk Simple Voice Chat.
4. Голосовые пакеты принимаются только при активной серверной сессии.
5. Ответ отображается как подписанный subtitle и, при успешном TTS, звучит пространственно от NPC.
6. `/livingworld end` завершает сессию и отменяет связанные операции.

Один игрок может владеть одной NPC-сессией, а один NPC не может одновременно разговаривать с несколькими игроками.

## Где я провёл границы

### Session ownership

Я не связываю право на разговор просто с фактом получения voice packet. Сначала сервер проверяет, что игрок действительно владеет активной сессией с этим NPC.

Для меня это важная деталь, потому что голосовой канал — всего лишь транспорт. Он не должен становиться обходным способом попасть в логику разговора.

### Context and memory

В prompt уходит не произвольное состояние Minecraft, а контекст, который заранее собрал сервер: идентичность NPC, разрешённые сведения о мире и сохранённая память разговора.

Так мне проще контролировать, что именно модель знает в конкретный момент, и не связывать память напрямую с форматом одного LLM-провайдера.

### Provider pipeline

```text
voice PCM → STT → validated text → LLM → bounded response → TTS PCM
text command ────────────────────┘
```

Каждый внешний этап я рассматриваю как потенциально ненадёжный. Если не сработал TTS, уже полученный текстовый ответ не должен пропасть. Если завис provider, сессия не должна навсегда остаться в промежуточном состоянии. Если разговор завершился, связанные операции должны отменяться.

### Action authorization

LLM не получает прямой доступ к игровому миру.

Даже если модель в будущем сможет предлагать действия, между её ответом и изменением состояния Minecraft остаётся отдельная серверная проверка. Мне не хочется строить систему, где текст из prompt или hallucination автоматически превращается в команду серверу.

## Как проходит запрос

![LivingWorld request lifecycle и trust boundaries](../../assets/diagrams/livingworld-request-lifecycle.svg)

Эту схему я сделал в первую очередь для себя, чтобы явно видеть, где меняется уровень доверия:

1. ввод игрока сначала проходит проверку владения сессией;
2. голос превращается в нормализованный текст, а не идёт напрямую в игровую логику;
3. контекст и память собирает сервер;
4. LLM формирует ответ или намерение, но не authoritative action;
5. потенциальное действие проходит отдельную validation/authorization границу;
6. cancellation и fallback проходят через весь pipeline.

Для меня смысл такой схемы в том, чтобы prompt injection, отказ provider или устаревший async-ответ не могли сами по себе изменить игровой мир.

## Что я проверяю автоматически

CI использует Java 21 и pinned artifacts MCA Reborn / Simple Voice Chat. Сейчас он проверяет:

- unit и package tests;
- reproducibility;
- Fabric game tests;
- multi-actor resilience scenarios;
- persistence и restart behavior;
- action/injection rejection;
- cancellation и fallback paths;
- server lifecycle;
- synthetic PCM и provider contracts;
- Simple Voice Chat runtime binding;
- multi-session ownership.

Успешная сборка публикует временный JAR artifact и SHA-256 checksum. Version tags могут публиковать тот же проверенный JAR в GitHub Releases.

## Что автоматическими тестами пока не доказать

Здесь я стараюсь не путать зелёный CI с готовностью реального multiplayer-сценария.

До deployment на friends/staging server всё ещё нужны:

- два совпадающих реальных клиента;
- реальные микрофоны;
- оценка качества русского STT;
- human-audible positional speech;
- provider degradation/recovery;
- backup и rollback rehearsal.

Для этого в проекте есть отдельный exact-JAR acceptance runbook.

## Что мне дал этот проект

LivingWorld оказался для меня удобным местом, где сошлись вещи, с которыми я обычно сталкиваюсь в backend, и совсем другой игровой runtime:

- серверная авторитетность;
- конкурентное владение ресурсом;
- внешние AI/voice providers;
- persistent state;
- security boundaries;
- воспроизводимая сборка и релиз.

Поэтому сейчас я воспринимаю его не как «чат-бота внутри Minecraft», а как небольшую агентную систему, которой приходится жить по правилам многопользовательского сервера.
