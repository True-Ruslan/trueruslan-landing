# TaskHub — Backend + AI

TaskHub я начинал как обычный проект управления задачами, но довольно быстро он стал для меня площадкой, где можно собрать в одном месте типичные backend-задачи и посмотреть, как они начинают взаимодействовать между собой.

В итоге здесь появились backend API, web-интерфейс, инфраструктурные сервисы и отдельный сценарий генерации технических задач через OpenRouter.

**Стек:** Java 21 · Spring Boot 3 · Spring Security · PostgreSQL · Liquibase · Redis · Kafka · ClickHouse · Docker Compose · OpenAPI

## Что мне было интересно проверить

Сам CRUD задач здесь никогда не был главной целью. Мне хотелось пройти чуть дальше и собрать небольшой продукт так, как будто у него уже есть разные эксплуатационные требования:

- где хранится основное состояние;
- как накатываются миграции;
- как подключается кеш;
- где появляется messaging;
- как отделить аналитическое хранилище;
- как встроить внешний AI-провайдер так, чтобы без него не перестала работать основная система;
- как всё это поднять локально без длинной инструкции на полдня.

## Как сейчас выглядит контур

```text
Web UI
  │
  ▼
REST API / Spring Boot
  ├── Task CRUD & business logic
  ├── AI generation → OpenRouter
  ├── Persistence → PostgreSQL / Liquibase
  ├── Cache & sessions → Redis
  ├── Messaging → Kafka
  └── Analytics storage → ClickHouse

Operations
  ├── Spring Actuator / health checks
  ├── OpenAPI / Swagger
  └── Docker Compose
```

## Что реализовано

- CRUD API для задач;
- отдельный endpoint генерации технических задач через AI;
- health endpoint для проверки AI-интеграции;
- Spring Security;
- PostgreSQL и Liquibase для схемы/миграций;
- Redis, Kafka и ClickHouse в инфраструктурном контуре;
- OpenAPI/Swagger документация;
- Spring Actuator и health checks;
- Docker Compose окружение;
- отдельный frontend.

## Несколько решений, которые я здесь оставил сознательно

### AI остаётся отдельной интеграцией

Мне не хотелось делать так, чтобы обычная работа с задачами зависела от доступности OpenRouter.

Поэтому AI-генерация существует как отдельный API-сценарий, а ключи и параметры провайдера приходят через конфигурацию. Если внешний сервис недоступен, это отдельная проблема интеграции, а не причина остановить весь task manager.

### Инфраструктуру можно поднять локально

PostgreSQL, Redis, Kafka, ClickHouse и вспомогательные UI запускаются через Docker Compose.

Для меня это полезнее, чем просто перечислить технологии в README. Можно действительно поднять окружение и посмотреть, как компоненты связаны между собой.

### Swagger и health checks я не считаю второстепенными

OpenAPI и Actuator здесь появились не «для галочки». Когда я сам возвращаюсь в проект спустя время, мне намного проще сначала открыть контракт API и health endpoints, чем заново восстанавливать картину только по коду.

## Проверки и сборка

В репозитории есть Maven-тесты и отдельные health endpoints. Базовый release-контур включает сборку, тестирование и публикацию Docker-образов через GitHub Actions.

## Где проект сейчас

MVP основного функционала завершён. Дальше я использую TaskHub скорее как инженерный sandbox: сюда удобно добавлять и проверять новые backend, infrastructure и AI-интеграции, не привязываясь к коммерческому продукту.
