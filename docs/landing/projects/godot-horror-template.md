# Godot Atmospheric Horror Template — agentic game development

Этот проект начался с довольно практичной проблемы. Когда я делал небольшие сцены на Godot, каждый новый эксперимент снова требовал собрать базовые вещи: движение, взаимодействия, двери, записки, свет, задачи, события и UI.

Мне захотелось один раз собрать нормальную основу для коротких atmospheric horror / walking-simulator игр и дальше развивать уже её, а не начинать каждый прототип с пустой сцены.

Отдельно мне было интересно проверить, как такой проект можно вести вместе с AI-агентами так, чтобы контекст не жил только в одном длинном чате.

## Как устроена основа

```text
Main / TemplateLevel
  ├── Player
  │   ├── first-person movement
  │   ├── mouse look
  │   └── flashlight
  ├── Interaction
  │   └── raycast / interactables
  ├── Objects
  │   ├── doors
  │   ├── notes
  │   └── light switch
  ├── Core
  │   ├── objectives
  │   └── horror event manager
  └── UI
      └── HUD / prompts / messages

Documentation layer
  ├── AGENTS.md
  ├── CONTEXT / TASKS / DECISIONS
  ├── DESIGN / EXPORT guides
  └── credits & licensing checklist
```

## Что уже есть

- first-person controller;
- mouse look;
- ходьба, бег и приседание;
- фонарик с зарядом;
- interaction raycast;
- интерактивные двери, записки и выключатель света;
- objective system;
- horror event manager;
- HUD с подсказками, задачами и сообщениями;
- запускаемая demo-room;
- минимальный playable flow: дверь → подсказка → записка → scripted event → финальное открытие двери.

## Что оказалось важнее самого шаблона

### Документация стала частью проекта

Сначала документация была просто способом не забывать принятые решения. Потом стало понятно, что при работе с AI-агентами это вообще отдельный слой архитектуры процесса.

В проекте появились точки входа вроде `START_HERE`, индекс документации, текущий контекст, задачи, решения, changelog, design/export guides и prompts.

Мне это нужно не ради формальности. После паузы или смены исполнителя гораздо полезнее начать с актуального состояния проекта, чем пытаться восстановить его из истории сообщений.

### Каждая итерация должна оставлять игру запускаемой

Я довольно быстро отказался от идеи генерировать большие куски проекта одним изменением.

Гораздо надёжнее добавлять ограниченный кусок функциональности, запускать игру, проверять сцену и только потом двигаться дальше. Это правило особенно полезно с агентной разработкой: большой diff может выглядеть убедительно, но скрывать десяток мелких несовместимостей между сценами, ресурсами и кодом.

### Лицензии лучше учитывать сразу

Игровой проект быстро обрастает чужими моделями, текстурами, звуками и шейдерами.

Поэтому я заранее добавил credits и licensing checklist. Иначе происхождение ассетов почти неизбежно превращается в задачу «разобраться потом», когда уже сложно вспомнить, откуда именно что появилось.

## Почему я продолжаю этот проект

Для меня он интересен не столько как конкретная horror-игра, сколько как эксперимент с самим способом разработки.

Здесь я проверяю, можно ли держать вместе код, сцены, документацию, UX небольшого demo-flow, решения по ассетам и работу AI-агентов так, чтобы проект можно было продолжать через много итераций без постоянной потери контекста.

По сути это попытка сделать не «идеальный универсальный шаблон», а понятную стартовую точку, которой я сам смогу пользоваться в следующих игровых проектах.
